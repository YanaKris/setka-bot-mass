# setka-bot-mass — стандарты разработки

Этот файл — источник правды по правилам работы в репозитории. Его читают двое:

- разработчик через Claude Code — файл подхватывается автоматически;
- авто-ревью в CI — промпт прямо ссылается на этот файл и требует отмечать каждое нарушение.

Описание проекта (архитектура, схема данных, API) — в [wiki](https://github.com/YanaKris/setka-bot-mass/wiki). Задачи с критериями приёмки — в [issues](https://github.com/YanaKris/setka-bot-mass/issues).

## TDD — без исключений

Каждое изменение production-кода начинается с теста:

1. написать тест на желаемое поведение;
2. запустить — увидеть **FAIL** с понятным сообщением;
3. написать минимальный код до **GREEN**;
4. прогнать все тесты — остаться зелёным;
5. отрефакторить, оставаясь зелёным.

«Слишком просто, чтобы тестировать» — не аргумент. Тест, написанный после кода, ничего не доказывает: он проходит сразу и не доказывает, что ловит регрессию.

Исключения — только по явному согласованию в issue (например, инфраструктурные задачи вроде docker-compose, где вместо автотестов фиксируется ручная проверка).

## ООП + SOLID

- **SRP**: один класс — одна ответственность. `SetkaClient` только ходит по HTTP, репозиторий только читает/пишет БД, сервис только оркестрирует.
- **DIP**: сервисы зависят от абстракций (`typing.Protocol` / ABC), реализации внедряются через конструктор, в роутах — через FastAPI `Depends`. В unit-тестах вместо реальных клиента и репозиториев подставляются фейки.
- **OCP**: новое поведение — новая реализация интерфейса, а не правка `if`/`match` в чужом классе.
- Слои: `api` → `services` → `repositories` / `clients` / `queue`. Бизнес-логика (`services`) **не импортирует** FastAPI, httpx и aio-pika — она ничего не знает про HTTP-фреймворк и брокер.

## DRY

Общий код живёт в одном месте: сборка Bearer-заголовка, разбор ответов «Сетки», маппинг статусов, фабрика сессий БД — в `core` и `clients`, переиспользуются процессами api и worker. Копипаст между `api` и `worker` запрещён.

## Тесты и покрытие

Пирамида:

1. **unit** — основная масса: сервисы с фейковыми репозиториями и клиентом, `SetkaClient` через `respx` (мок httpx). Без реальных БД и брокера.
2. **integration** (`@pytest.mark.integration`) — репозитории против реального PostgreSQL, publisher и consumer против реального RabbitMQ из docker-compose.
3. **e2e** — полный сценарий против mock-сервера «Сетки»: создать кампанию → start → worker отправил → статусы и `sent_log` корректны.

Пороги: **≥ 85 % всего** (gate в CI), **≥ 90 % для `services`, `clients`, `repositories`**. Покрытие — следствие TDD, а не самоцель: тестируем поведение, а не строки.

Node-скрипты авто-ревью покрываются тестами `node:test` рядом с модулем (`*.test.mjs`) — они тоже gate в CI.

## Безопасность

- `bearer_token` пользователя хранится в БД в открытом виде — принятое ограничение внутреннего инструмента. В публичный контур приложение выносить нельзя.
- Токен **никогда** не пишется в логи и не возвращается в ответах API — в схемах ответа поле исключено.
- Секреты не коммитятся: конфигурация только из env / `.env`, в коде нет захардкоженных URL и токенов.

## Команды

```bash
make install-dev   # pytest, pytest-cov, ruff, diff-cover
make test          # быстрый прогон тестов
make cov           # тесты + покрытие, порог 85 %
make lint          # ruff check + ruff format --check
make fmt           # автоисправление
make test-scripts  # тесты node-скриптов авто-ревью
make check         # всё, что гоняет CI
```

## Рабочий процесс

Одна задача = один issue = одна ветка = один PR.

Ветку называем по номеру issue — `7-create-campaign` (именно так GitHub называет ветки, создаваемые кнопкой «Create a branch» в issue). В теле PR ставим `Closes #7`.

Это не косметика: авто-ревью ищет номер issue в теле PR (`Closes/Fixes/Resolves #N`), затем в префиксе ветки, затем в заголовке PR — и подтягивает критерии приёмки задачи в промпт. Без привязки ревью пройдёт без контекста задачи и не проверит выполнение критериев.
